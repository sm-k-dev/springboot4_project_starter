# 조사: 저장 방식(JSON vs SQLite)과 CLI 라이브러리(argparse vs click)

작성: 지훈 (리서처) · 요청: 민준 · 대상 문서: `docs/design.md`

## 0. 결론 요약

| 항목 | 추천 | 한 줄 근거 |
|---|---|---|
| 저장 방식 | **JSON 파일 (설계 그대로)** | 할 일 수백 개, 기능 3개, 단일 사용자 규모에서 SQLite는 과합니다. |
| CLI 라이브러리 | **argparse (설계 그대로)** | 표준 라이브러리만 쓰는 설계 제약을 지키며, 명령 3개에는 충분합니다. |
| 설계 타당성 | **타당함. 아래 "보완 필요 사항" 4가지만 반영 권장** | 특히 Python 3.9 타입 힌트 문제는 구현 전에 고쳐야 합니다. |

## 1. 저장 방식: JSON 파일 vs SQLite

### 1.1 비교

| 기준 | JSON 파일 | SQLite (`sqlite3`, 표준 라이브러리) |
|---|---|---|
| 외부 의존성 | 없음 | 없음 (`sqlite3`은 표준 라이브러리) |
| 구현 분량 | 적음. 읽기 → 수정 → 원자적 쓰기 | 중간. 스키마 생성, 커넥션 관리, SQL 작성 |
| 사람이 직접 확인 | 가능 (텍스트) | 별도 도구 필요 (바이너리) |
| 동시 실행 안전성 | 원자적 교체로 **파일 깨짐은 막지만, 두 프로세스가 동시에 쓰면 한쪽 변경이 사라질 수 있음** (마지막 쓰기 우선) | 트랜잭션과 잠금으로 **변경 손실 방지** |
| 데이터 규모 | 수백~수천 건까지 충분. 쓸 때마다 전체 파일을 다시 씀 | 수백만 건까지 여유 |
| 기능 확장(삭제, 수정, 검색, 필터) | 항목이 많아지면 매번 전체를 읽고 쓰는 부담 | 인덱스, 쿼리로 자연스럽게 처리 |
| 스키마 변경(마이그레이션) | `version` 필드로 직접 처리 | `PRAGMA user_version` 등으로 직접 처리 |
| 테스트 | `tmp_path`에 파일 생성으로 간단 | `:memory:` 또는 `tmp_path` DB로 간단 |

### 1.2 추천: JSON 파일

- 이번 범위는 추가·목록·완료뿐이고 삭제, 수정, 검색은 범위 밖입니다. 이 규모에서 SQLite의 장점(동시성, 쿼리, 인덱스)은 쓰이지 않습니다.
- 설계 8장의 근거("DB는 과합니다")에 동의합니다.
- 주의할 점: 설계에서 SQLite를 "외부 의존성 때문에 안 된다"고 적으면 틀린 근거가 됩니다. `sqlite3`은 표준 라이브러리이므로 의존성 제약은 해당하지 않습니다. JSON을 고르는 이유는 **규모와 기능 범위**입니다. 문서의 근거 문장을 이 방향으로 정정하면 좋겠습니다.
- 나중에 삭제·검색·여러 사용자가 추가되면 SQLite 전환을 다시 검토하세요. 그때는 `storage.py`만 바꾸면 되도록 `load_tasks` / `save_tasks` 인터페이스를 유지하는 현재 설계가 전환 비용을 낮춥니다.

## 2. CLI 라이브러리: argparse vs click

### 2.1 비교

| 기준 | argparse (표준 라이브러리) | click (서드파티) |
|---|---|---|
| 외부 의존성 | 없음 | `pip install click` 필요 |
| 설계 제약("표준 라이브러리만") 충족 | **충족** | **위반** (개발 의존성이 아닌 런타임 의존성이 됨) |
| 하위 명령 구현 | `add_subparsers()`로 가능. 코드가 조금 길어짐 | 데코레이터(`@click.group`, `@click.command`)로 짧고 명확 |
| 인자 검증(`type=int`) | 기본 지원. 실패 시 종료 코드 2 | 지원. 실패 시 종료 코드 2 |
| 도움말 자동 생성 | 지원 | 지원 (더 보기 좋은 출력) |
| 테스트 | `main(argv)`를 직접 호출하면 충분 (설계 6장과 일치) | `CliRunner` 제공 (편리하지만 필수는 아님) |
| 학습 비용 | 표준 문서만 보면 됨 | 별도 문서 필요 |

### 2.2 추천: argparse

- 설계의 "표준 라이브러리만 사용" 제약을 그대로 지킵니다.
- 명령이 3개이고 `main(argv)` 구조로 테스트할 수 있으므로 click의 장점(간결함, CliRunner)이 필요할 만큼 크지 않습니다.
- 종료 코드 2(사용법 오류)는 argparse의 기본 동작과 설계 4장 표가 일치합니다.

## 3. 설계 타당성 의견

전체적으로 **타당합니다.** 범위가 작고 계층 분리(`cli → service → storage/task`)가 명확해서 테스트하기 쉽습니다. 아래 사항은 구현 전에 반영하는 것을 권장합니다.

### 3.1 [중요] Python 3.9 타입 힌트 문제

설계 5장 `def main(argv: list[str] | None = None)` 과 `tuple[list[Task], Task, bool]` 등에서 `X | None` 형식을 쓰고 있습니다.
Python 3.9에서는 `X | None`이 **함수 정의 시점에 실행되어 `TypeError`가 발생**합니다(PEP 604는 3.10부터 실행 시 지원). `list[Task]`처럼 소문자 제네릭은 3.9에서 동작합니다.

- 권장: 각 파일 상단에 `from __future__ import annotations`를 두거나, `Optional[list[str]]`로 씁니다.
- 설계 1장의 "Python 3.9 이상"을 유지한다면 이 처리가 필요합니다. 3.10 이상으로 올린다면 그대로 두어도 됩니다. 어느 쪽인지 `pyproject.toml`에 명시하세요.

### 3.2 [권장] 원자적 쓰기에 `fsync` 추가

설계 3장은 `<path>.tmp`에 쓴 뒤 `os.replace`로 교체한다고 되어 있습니다. 이것만으로는 정전이나 시스템 강제 종료 시 교체된 파일이 비어 있거나 덜 쓰인 상태로 남을 수 있습니다.

- 권장 순서: 임시 파일에 쓰기 → `flush()` → `os.fsync(f.fileno())` → `os.replace(tmp, path)`.
- 임시 파일은 반드시 **같은 폴더**에 만들어야 `os.replace`가 원자적으로 동작합니다. 설계의 `<path>.tmp`는 이를 만족합니다.
- 테스트에서는 "임시 파일이 남지 않음"만 검증하고 fsync 자체는 검증하지 않아도 됩니다.

### 3.3 [권장] 동시 실행 시 변경 손실 (설계에 없음)

두 터미널에서 `todo add`를 거의 동시에 실행하면, 둘 다 같은 파일을 읽고 각자 쓰기 때문에 한쪽 추가가 사라질 수 있습니다. 파일이 깨지지는 않습니다.

- 개인용 CLI이고 설계 범위가 단일 사용자라면 **알려진 제한으로 명시**하는 것으로 충분합니다.
- 막고 싶다면 `fcntl`(POSIX) 또는 잠금 파일을 쓰는 방법이 있지만, Windows 호환성 문제가 생기므로 표준 라이브러리만으로는 간단하지 않습니다. 이 경우에도 SQLite가 더 간단한 해법이라는 점은 1장과 같습니다.
- 권장: 설계 3장에 "동시 실행은 지원하지 않음" 한 줄을 추가합니다.

### 3.4 [권장] `add` 인자가 없을 때의 동작 명시

설계 4장은 빈 내용을 종료 코드 1로 정의하지만, `todo add`처럼 인자가 아예 없는 경우는 다루지 않습니다.

- `nargs="+"`로 두면 인자 누락은 argparse가 종료 코드 **2**로 처리합니다.
- `nargs="*"`로 두고 빈 문자열로 합치면 종료 코드 **1**(`오류: 할 일 내용이 비어 있습니다.`)이 됩니다.
- 권장: 어느 쪽인지 정해 설계 4장에 적습니다. 사용자 입장에서는 `nargs="*"`로 두고 종료 코드 1을 주는 편이 "빈 내용"이라는 한 가지 오류로 통일되어 일관적입니다.

### 3.5 [사소] 기타 확인 사항

- `pyproject.toml`의 `pythonpath = ["src"]`는 pytest 7 이상에서 지원됩니다. 개발 의존성 버전을 `pytest>=7`로 명시하세요.
- `todo add -h`처럼 `-`로 시작하는 내용은 argparse가 옵션으로 해석합니다. 필요하면 `--` 구분자 사용을 안내 문구에 넣으세요. 이번 범위에서는 문서화만으로 충분합니다.
- `done`의 id `0`이나 음수는 정수 파싱은 통과하고 `TaskNotFound`(종료 코드 1)가 됩니다. 설계와 일치합니다.
- 설계 7장 진행 순서에서 서연은 수아의 `docs/ui.md`를 기다립니다. 수아의 문구가 4장과 다르면 `cli.py`의 문구 상수를 한 곳에 모으면 수정이 쉽습니다.

## 4. 보완 필요 사항 요약 (우선순위순)

1. **[중요]** 3.9 호환을 위해 `X | None` 타입 힌트 수정 (`from __future__ import annotations` 또는 `Optional`).
2. **[권장]** 원자적 쓰기에 `flush` + `os.fsync` 추가.
3. **[권장]** 동시 실행 미지원을 설계 문서에 명시.
4. **[권장]** `todo add`(인자 없음)의 종료 코드를 확정해 4장 표에 반영.
5. **[사소]** `pytest>=7` 명시.

## 5. 근거와 한계

- 이 조사는 설계 문서(`docs/design.md`)와 Python 표준 라이브러리의 일반적인 동작을 바탕으로 한 **문서 검토**입니다. 실제 코드를 실행해 확인하지는 않았습니다.
- 3.1의 Python 3.9 `X | None` 동작은 PEP 604에 따른 것입니다. 구현 단계에서 `python3.9 -c` 등으로 한 번 확인하면 확실합니다.
- click의 기능 설명은 일반적인 사용 기준이며, 버전별 세부 차이는 확인하지 않았습니다.
